## ADR : 온보딩 여부 판별 로직에 has_schedule 컬럼 추가
### 작성일

2025-10-13

### 컨텍스트

온보딩이 필요한 유저(= 생성된 일정이 없는 유저)를 선별하기 위한 신규 API를 설계하고자 한다.

이 API는 유저가 앱에 진입했을 때, 온보딩 화면을 보여줄지 여부를 판단하는 용도로 사용된다.

이때, 스케줄 존재 여부를 어떤 방식으로 판별할지에 대해 다음과 같은 접근 방식을 검토했다.

1. 로그인된 유저 정보를 조회한다.
2. 해당 유저의 ID로 스케줄 존재 여부(`exists by userId`)를 조회한다.
3. 스케줄이 없으면 `true`, 있으면 `false`로 API 응답을 반환한다.

이 방식은 단순하지만, 앱 진입 시마다 스케줄 테이블 조회가 발생하므로 온보딩이 끝난 이후에도 불필요한 조회 비용이 계속 발생한다.

앱 진입은 일정 생성보다 훨씬 빈번하기 때문에, 장기적으로 조회 부하가 커질 수 있다.

이를 해결하기 위해 아래의 세 가지 대안을 검토했다.

### 대안

### **① 앱 진입 시 실시간 스케줄 조회 방식**

- **설명:** 앱 진입 시마다 스케줄 테이블에서 `exists by userId`를 실행해 온보딩 여부를 판단한다.
- **장점:** 컬럼 추가 없이 단순하게 구현 가능. 실시간 조회이기 때문에 정합성 보장이 용이하다.
- **단점:** 앱 진입 트래픽이 높아질수록 반복 조회에 따른 DB 부하가 누적된다. 온보딩이 끝난 유저에게도 불필요한 조회가 계속된다.

### **② 캐시 저장소(예: Redis)에 온보딩 여부 저장**

- **설명:** 유저의 온보딩 여부를 Redis 등에 캐싱해두고, 앱 진입 시 캐시에서 바로 조회한다.
- **장점:** DB 조회 없이 빠르게 응답 가능.
- **단점:** 캐시 만료 정책, 동기화 로직이 필요해 시스템 복잡도가 올라간다. 장애나 만료 시 fallback 로직도 설계해야 한다.

### **③ 유저 테이블에 `has_schedule` 컬럼을 추가하여 상태 관리 (선택)**

- **설명:** 유저 최초 생성 시 `has_schedule = false`로 초기화하고, 일정 생성 시 `false`인 경우에만 `true`로 업데이트한다. 앱 진입 시에는 이 컬럼만 조회하여 온보딩 여부를 판단한다.
- **장점:** 앱 진입 시 스케줄 조회 없이 단건 조회만으로 판별 가능. 온보딩 이후에는 추가 조회가 전혀 없다. 구현 난이도가 낮고, 정합성 유지도 단순하다.
- **단점:** 스케줄 데이터와 컬럼 간 정합성을 위한 최소한의 후처리 로직(예: 모든 스케줄 삭제 시 컬럼 되돌리기)이 필요하다.

### 결정

**③ 유저 테이블에 `has_schedule` 컬럼을 추가하여 상태를 관리하는 방식을 채택**한다.

- 앱 진입이 일정 생성보다 훨씬 빈번하다는 트래픽 특성상, 앱 진입 시 조회를 최소화하는 방식이 효율적이다.
- 캐시 방식은 추가적인 인프라 및 동기화 복잡도를 수반하며, 단순한 불리언 상태 관리에 비해 과도하다.
- 실시간 조회 방식은 구현은 간단하지만 장기적으로 DB 부하를 증가시킬 수 있다.
- 반면, 컬럼 방식은 앱 진입 시 단건 조회만으로 온보딩 여부를 알 수 있고, 일정 생성 시에도 스케줄 조회 없이 컬럼 상태만 갱신하면 되므로 전체적인 조회 부하를 크게 줄일 수 있다.

### 결과

- 앱 진입 시 조회 비용이 스케줄 exists 쿼리(최소 1~2회)에서 **유저 단건 조회 1회**로 감소한다.
- 온보딩이 끝난 유저에 대해서는 스케줄 조회 없이 컬럼만으로 판별할 수 있어 **반복 조회 비용이 완전히 제거**된다.
- 일정 생성 시에도 스케줄 조회 없이 컬럼 상태만 확인해 업데이트하므로 쿼리 수를 최소화할 수 있다.
- 정합성 유지 로직은 단순하며, 시스템 복잡도도 낮다.
