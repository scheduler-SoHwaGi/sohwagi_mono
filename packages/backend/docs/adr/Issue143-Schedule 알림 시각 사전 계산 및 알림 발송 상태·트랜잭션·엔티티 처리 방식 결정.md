## ADR : Schedule 알림 시각 사전 계산 및 알림 발송 상태·트랜잭션·엔티티 처리 방식 결정
### 작성일
2025-12-15

### 컨텍스트
Schedule 도메인에 일정 시각 15분 전 푸시 알림 기능을 도입한다.
알림은 스케줄러를 통해 주기적으로 처리되며, 다음과 같은 설계 이슈를 함께 고려해야 했다.
1. 알림 시각을 언제 계산, 관리할 것인가.
2. 알림 중복 발송을 어떻게 방지할 것인가.
3. 외부 시스템(Firebase) 호출 이후 상태 변경을 어떻게 안전하게 처리할 것인가.
4. 트랜잭션 경계 밖에서 조회된 엔티티(detached entity)를 어떻게 다룰 것인가.

특히 JPA 환경에서 리스트 조회 -> 외부 호출 -> 상태 변경 흐름은 엔티티 영속성 상태 및 트랜잭션 경계 설정에 따라 데이터 정합성 문제가 발생할 수 있다.

### 결정
1. `nofied_at` 컬럼 도입 (알림 시각 사전 계산)
   - Schedule 테이블에 `notified_at` 컬럼을 추가한다.
   - Schedule 생성 시점에 `notifiedAt = scheduledAt - 15분`을 계산하여 저장한다.
   - 알림 대상 조회 기준은 다음과 같다.
   ```
    notified_at >= now - 1m
    AND notified_at <  now
    ```
2. `notified` 컬럼 도입 (알림 발송 상태 관리)
   - 알림 중복 발송을 방지하기 위해 `nofied (boolean)` 컬럼을 추가한다.
   - 알림 대상 조회 시 해당 조건(=false)을 함께 사용한다.
   - 알림이 정상적으로 전송된 이후에만 `notified = true` 상태로 변경한다.
3. 알림 전송 순서 결정
   - 알림 전송 로직은 다음 순서를 따른다.
     1. 알림 대상 Schedule 조회
     2. 외부 시스템(Firebase)을 통한 푸시 알림 전송
     3. 푸시 전송 성공 이후 Schedule 상태 변경
   - 외부 호출 이전에 상태를 변경하지 않음으로써 알림 유실 및 잘못된 상태 확정을 방지한다.
4. 트랜잭션 범위 최소화
   - 메서드 전체(Facade 레벨, 스케줄 리스트 조회 후 알림 전송 로직)를 하나의 트랜잭션으로 묶지 않는다.
   - 외부 시스템 호출(Firebase)은 트랜잭션 외부에서 수행한다.
   - 해당 성공 알림건의 스케줄 상태 변경만 트랜잭션으로 감싼다.
5. ID 기반 재조회 후 상태 변경 (Detached Entity 방지)
   - 트랜잭션 경계 밖에서 조회된 Schedule 엔티티는 영속 상태가 아닐 수 있으므로, 다음 방식을 채택한다.
     - 상태 변경 시 엔티티 객체 자체를 전달하지 않는다.
     - Schedule ID만 전달하여 트랜잭션 내부에서 재조회한다.
     - 양속 상태의 엔티티에 대해서만 상태 변경을 수행한다.
   - 이를 통해 JPA의 dirty checking를 안정적으로 보장한다.

### 결과
이 결졍으로 다음과 같은 효과를 얻는다.
- 알림 시각 계산 로직이 사전 계산(`notified_at`)으로 고정되어 조회 및 배치 로직이 단순해진다
- `notified` 상태 컬럼을 통해 알림 중복 발송을 안정적으로 방지할 수 있다
- 외부 시스템 호출 실패 시 알림 상태가 잘못 변경되지 않아 재시도가 가능하다
- 트랜잭션 범위를 최소화하여 DB 리소스 점유 및 락 유지 시간을 줄인다
- ID 기반 재조회 방식을 통해 Detached Entity로 인한 변경 누락 위험을 제거한다

### 대안
- 대안 1 : 엔티티 객체를 그대로 전달하여 상태 변경
  - 문제점
    - 트랜잭션 경계 밖에서 조회된 엔티티는 detached 상태일 수 있음
    - 변경 감지가 보장되지 않아 상태 변경 누락 가능
